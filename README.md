# taste-signal

카카오맵 별점에서 맛에 대한 신호만 남겨서, 이 식당이 맛있는지를 구간으로 보여 주려는 프로젝트다.

조작 여부는 판정하지 않는다. 판정은 만들 수 없다는 것이 이 프로젝트의 첫 결론이고, 근거는 METHOD.md 에 적었다.

## 1. 지금 상태

| 부분 | 상태 |
|---|---|
| 리뷰어 편차와 그 95% 구간 | 구현 |
| 정답 레이블 없는 검증 (구간, 반분 신뢰도, 조작 비용) | 구현 (validate.py) |
| 후기 본문 측면 분류 (맛, 응대, 웨이팅, 가격, 기타) | 레이블 완료. 규칙 분류기는 기준에 못 미쳤고, 레이블은 LLM 이 달고 사람이 일부 검수했다 |
| 맛 점수와 등급 | 첫 결과 (3절 끝) |

설계는 METHOD.md 의 4절부터 6절에 있다.

## 2. 무엇을 계산하나

별점에는 맛 말고도 여러 가지가 섞여 있다. 두 가지를 걷어 낸다.

첫째, 리뷰어의 평소 기준. 카카오맵은 후기마다 작성자의 총 후기 수와 평균 별점을 함께 보여 준다.
평소 4.9를 주는 사람이 준 5점은 +0.1이고, 평소 3.2를 주는 사람이 준 5점은 +1.8이다.
이 차이를 편차라고 부른다. 노출되는 평균에는 그 후기 자신이 들어 있으므로 그 후기를 뺀 평균을
다시 구해서 쓴다. 평균이 소수 한 자리로 반올림되어 노출되기 때문에 후기가 5개 미만인 리뷰어는
계산하지 않는다.

둘째, 맛이 아닌 이유. 불친절, 웨이팅, 가격 때문에 깎인 별점은 맛에 대해 아무것도 말해 주지 않는다.
후기 본문을 측면별로 분류해서, 맛을 언급하지 않은 후기는 맛 계산에서 뺀다.

이때 별점이 높든 낮든 똑같이 뺀다. 깎은 후기만 빼고 올린 후기는 남기면 걸러 낼수록 평점이
오르기만 하고, 응대가 나쁜 가게일수록 많이 걸러져서 가장 많이 오른다. "친절해요" 한 줄로 5점을
준 후기도 맛에 대해서는 말해 주는 것이 없기는 마찬가지다.

맛이 아닌 측면은 버리지 않고 따로 보여 준다. 웨이팅을 감수할지는 보는 사람이 정할 일이다.

출력은 순위가 아니라 등급이다. 95% 구간이 겹치는 가게끼리는 같은 등급으로 묶는다.

## 3. 측정한 것

2026년 9월 18일, 서울 마포구 연남동과 홍대 일대 고깃집 11곳의 카카오맵 후기 1,209건.
정답 레이블이 없어서 정확도는 잴 수 없다. 대신 레이블 없이 잴 수 있는 세 가지를 쟀다.
가게 이름은 기호로 바꿨다(5절).

### 편차의 95% 구간

리뷰어를 2,000번 재표집했다.

| 가게 | 편차 | 95% 구간 | 리뷰어 수 |
|---|---|---|---|
| A | +0.68 | +0.52 에서 +0.84 | 103 |
| B | +0.66 | +0.24 에서 +1.05 | 48 |
| C | +0.63 | +0.31 에서 +0.93 | 29 |
| D | +0.58 | +0.37 에서 +0.76 | 61 |
| E | +0.39 | +0.02 에서 +0.81 | 18 |
| F | +0.32 | +0.17 에서 +0.48 | 111 |
| G | +0.27 | +0.04 에서 +0.50 | 75 |
| H | +0.26 | -0.04 에서 +0.57 | 63 |
| I | +0.08 | -0.16 에서 +0.29 | 38 |
| J | -0.24 | -0.35 에서 -0.14 | 115 |
| K | -0.69 | -1.08 에서 -0.29 | 50 |

상위 네 곳의 구간이 서로 겹친다. 점추정으로는 A가 1위지만 구간으로는 A부터 D까지 가를 수 없다.
그래서 순위 대신 등급을 쓴다.

가게 B의 값은 틀린 표본에서 나왔다. 첫 수집 때 B만 전체 후기 중 일부를 받았는데, 그것이 카카오맵
추천순의 앞부분이었다. 10월 6일 최신순으로 전수를 받으니 B의 편차는 -0.11(구간 -0.25 에서 +0.02)이다.
경위는 METHOD.md 3절.

### 반분 신뢰도

후기를 무작위로 반씩 나눠 양쪽에서 가게 순위를 따로 매기고, 두 순위의 스피어만 상관을 500번 구했다.

| 지표 | 중앙값 | 5퍼센트에서 95퍼센트 |
|---|---|---|
| 편차 | 0.72 | 0.46 에서 0.88 |
| 원평균 | 0.69 | 0.49 에서 0.87 |
| 보정 평점 (가중과 수축) | 0.45 | 0.22 에서 0.68 |

편차의 장점은 재현성이 아니다. 원평균과 비슷하다. 보정 평점은 가장 나빠서 주 출력에서 뺐다.

### 조작 비용

가짜 5점을 몇 개 넣어야 지표가 0.1 움직이는지 쟀다.

| 가게 (원평균, 편차) | 공격 계정 | 원평균 | 편차 |
|---|---|---|---|
| I (4.77, +0.08) | 후기 1개, 평균 5.0 | 109 | 움직이지 않음 |
| | 후기 10개, 평균 4.3 | 109 | 7 |
| | 후기 30개, 평균 4.0 | 109 | 5 |
| J (4.62, -0.24) | 후기 1개, 평균 5.0 | 41 | 움직이지 않음 |
| | 후기 30개, 평균 4.0 | 41 | 10 |
| A (4.57, +0.68) | 후기 1개, 평균 5.0 | 36 | 움직이지 않음 |
| | 후기 30개, 평균 4.0 | 36 | 41 |

편차는 일회성 계정에는 움직이지 않는다. 그러나 후기를 쌓은 계정으로는 원평균보다 싸게 움직이는
가게가 있고, 편차가 낮은 가게일수록 싸다. 순위를 올리고 싶은 쪽이 바로 편차가 낮은 가게이므로,
동기가 가장 큰 곳에서 방어가 가장 약하다. 11곳 전체 표는 validate.py 가 출력한다.

### 맛 점수 첫 결과

10월 6일에 같은 11곳의 후기 2,150건을 날짜와 본문까지 다시 받아, 맛을 언급하지 않은 후기를 빼고
계산했다. 등급은 맛 편차의 95% 구간으로 묶었다. 전체 편차는 같은 날 전수 기준이다.

걸러진 비율은 별점이 본인 평균보다 낮은 후기 가운데 맛 이야기가 없어서 빠진 비율이다.

가게 B는 전체 편차 -0.11에서 맛 편차 +0.24로 올라간다. 낮은 별점의 38퍼센트가 맛 이야기 없이 응대와
웨이팅을 탓한 후기였다. 이 기능이 고치려던 경우가 그대로 나타났다.

가게 K는 -0.69에서 -0.16으로 올라간다. 다만 쓰인 후기가 22건이라 구간이 넓고, 규칙 분류기로 레이블을
달면 -0.62에 그친다. 11곳 전체로는 두 레이블의 가게 순위상관이 0.88인데, K에서만 크게 갈린다.
결론이 분류기에 가장 많이 달린 가게가 이 기능의 대표 사례다.

가게 J는 맛을 언급한 후기의 99퍼센트가 긍정인데 맛 편차는 가장 낮다. 본문은 칭찬인데 별점은 본인
평소보다 낮다. 리뷰어들의 평소 평균이 5점에 붙어 있어서 4점 몇 개가 크게 깎는다. 해석은 보류한다.

맛 편차의 반분 신뢰도는 0.74로, 같은 날 전수 기준 전체 편차의 0.78보다 조금 낮다. 걸러 낸 만큼
표본이 줄었기 때문이다.

## 4. 실행

```
python3 -m unittest
python3 report.py
python3 validate.py
```

테스트는 데이터 없이 돈다. report.py 와 validate.py 는 data/reviews.csv 가 필요한데, 이 파일은
저장소에 없다(5절). 형식은 아래와 같다.

```
shop,reviewer_count,reviewer_avg,star,paid
가게이름,91,4.7,5.0,True
```

reviewer_count 는 작성자의 총 후기 수, reviewer_avg 는 작성자의 평균 별점(이 후기 포함, 소수 한 자리),
star 는 이 가게에 준 별점, paid 는 결제인증 표시 여부다. validate.py 는 난수 시드가 고정되어 있어서
같은 데이터면 같은 숫자를 낸다.

## 5. 데이터를 저장소에 넣지 않는 이유

수집한 데이터, 수집 도구, 가게 이름을 공개하지 않는다.

카카오맵의 robots.txt 는 map.kakao.com 과 place.map.kakao.com 모두 모든 자동 접근을 막고 있고,
AI 학습과 검색 증강 생성 목적의 접근은 엄격히 금지한다고 적고 있다(2026년 10월 6일 확인).
후기 본문은 작성자의 글이다. 그리고 특정 가게의 이름을 붙여 평점의 신뢰도를 공개하는 일은,
통계 결과라 해도 그 가게에 불이익을 줄 수 있다.

그래서 이 저장소는 방법과 검증 코드만 담는다. 결과표의 가게는 편차 순서대로 A부터 K까지 기호를 붙였다.

## 6. 한계

리뷰이벤트는 걸러 낼 수 없다. 음료 하나를 받고 5점을 주는 사람은 실제로 방문한 실제 손님이고,
평소 쓰던 계정으로 "맛있어요"라고 쓴다. 리뷰어 편차에도 측면 분류에도 걸리지 않는다.
측면 분류가 고치는 것은 맛이 아닌 이유로 억울하게 깎인 별점이지, 부풀려진 별점이 아니다.
텍스트를 쓰는 데에는 비용이 들지 않는다.

후기를 쌓은 계정을 쓰는 대행에는 편차가 오히려 약한 가게가 있다. 3절 조작 비용 표가 그것이다.

리뷰어의 평균 별점은 수집한 시점의 값이다. 2022년에 쓴 후기에 2026년의 평균을 대는 셈이다.
관대함은 사람의 안정된 성향이라고 보고 쓰지만 가정이다.

조작 여부의 정답 레이블은 존재하지 않는다. 따라서 이 점수의 정확도는 측정할 수 없고 앞으로도
측정할 수 없다. 정확도 수치를 붙여 말하지 않는다.

측면 레이블은 사람이 처음부터 단 것이 아니다. LLM 이 달고, 사람이 300건을 읽으며 틀린 것을 골랐다.
일부러 틀리게 바꾼 항목 15개 중 9개를 사람이 잡았다. 긍정과 부정을 뒤집은 것은 10개 중 8개를
잡았지만, 무난함과 긍정, 언급 없음과 부정의 경계는 거의 잡지 못했다. 경위는 METHOD.md 6절.
